## 1. Executive Summary

This Architecture Impact Check evaluates the architectural and operational consequences of adding **Dynamic Custom Fields**, **Extended Contact/Entity Core Fields**, and a **Typed Filter AST Query Engine** with **Saved Presets** to the Spark Finance & Studio Manager desktop application.

---

## 2. Impact Dimensions

### 2.1 Domain Layer
- **No Leads / No CRM**: In strict adherence to system authority, no leads, stages, pipeline funnels, or prospective customer concepts were introduced. The system manages actual clients and services only.
- **Service Derivation**: Services are not stored as dummy arrays or arbitrary tags; they are derived dynamically from actual historical records (`marketing_contracts`, `subscriptions`, `website_projects`, `studio_bookings`, `client_packages`).
- **Money & Measurement Invariants**: Custom money fields store amounts strictly as integer piasters (`number_value INT`). Dates are validated as ISO-8601 UTC strings.

### 2.2 Data & Persistence Layer
- **Relational Normalization vs JSON Blobs**: Rather than storing arbitrary custom fields in a single untyped JSON blob inside the `clients` table, a normalized relational schema was chosen:
  - `client_custom_field_definitions`
  - `client_custom_field_options`
  - `client_custom_field_values`
  - `client_custom_field_multiselect_values`
  - `client_filter_presets`
- **Zero-Loss Migrations**: Migration 003 is purely additive. It alters `clients` to add nullable columns with default values (`client_type` default `'individual'`, `preferred_contact` default `'phone'`). Existing records remain 100% intact.
- **Foreign Key Constraints & Cascade Safeguards**:
  - Values cascade delete with clients (`ON DELETE CASCADE`).
  - Definitions cannot be hard-deleted if client values exist; the domain layer throws `DomainInvariantError` requiring deactivation instead.
  - Type changes on definitions are prohibited if values already exist.

### 2.3 State & Transactions
- **Atomic Operations with Complete Rollback**: Client creation and custom field value persistence run inside a single SQLite transaction (`driver.transaction`). Any validation error or constraint failure completely rolls back the client record and all values.
- **Query Layer**: Filter AST evaluation and global searches are executed inside SQLite queries rather than in-memory `Array.filter` within React. Financial balances (outstanding dues, credit, active contracts) are calculated via SQLite subqueries to prevent N+1 performance bottlenecks.

### 2.4 Security & Threat Model
- **SQL Injection Prevention**: All queries generated by the Filter AST compiler use strict parameter binding (`?`). Field keys and operator strings are strictly verified against an allowlist of valid core and active custom fields.
- **Input Sanitization**: Phone numbers are normalized (spaces/dashes removed); emails and URLs are validated via regex before persistence.

### 2.5 Reliability & Fault Tolerance
- **Deactivated Fields Handling in Presets**: When a saved filter preset references a custom field that was subsequently deactivated, the query compiler gracefully skips the inactive rule and the UI displays a gentle warning banner rather than crashing or deleting the preset.
- **Safe Archiving**: Archiving a client sets `active = 0`, keeping all associated contracts, custom field values, and financial records intact.

### 2.6 Deployment & Desktop Integrations
- **Offline Desktop Runtime**: Retains 100% offline functionality within Tauri v2 with zero external API dependencies.
- **Build Artifacts**: Production build verified clean with Vite and `tsc` (`dist/` generated without type or bundle errors).
